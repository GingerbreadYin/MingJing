# 制作过程中实际遇到的问题

日期：2026-11-03。这里记录亲自遇到或通过审查复现的问题；常见但未亲历的问题另见 TROUBLESHOOTING.md。

| 问题 | 现象与根因 | 处理与验证 | 学习重点 |
|---|---|---|---|
| Git 仓库所有权不同 | 读取原 RAG 时出现 dubious ownership；原目录由另一运行身份创建 | 只在指定仓库的命令使用精确 safe.directory，未设置全局通配信任；提交与交接一致，工作区干净 | 环境权限问题与代码问题分开 |
| uv 默认缓存不可写 | AppData 临时缓存 persist 出现 access denied | 新环境显式使用 D 盘项目缓存；Python 3.12 环境建立成功 | 缓存、解释器、项目环境是不同路径 |
| 上游克隆/检出停滞 | 部分克隆后媒体/源码对象下载长时间无输出；中断留下空 index.lock | 确认没有 Git 进程后只清理本次锁；浅层获取固定提交并稀疏检出后端、前端源码、配置 | 锁存在时不能直接假定可删除；不要下载全部历史和演示媒体 |
| Python 包下载超时 | 固定锁文件安装时多个下载重试后超时 | 保持版本不变，降低并发到 4 并复用缓存，最终安装完成；没有靠升级版本掩盖网络问题 | 网络失败与依赖不兼容不同 |
| 缺少 Git 作者身份 | 本地提交提示 Author identity unknown | 每次提交显式使用 Codex 本地工具身份，未冒充用户或改全局配置 | 工具生成与个人贡献要可追溯 |
| SQLite 文件无法释放 | Windows 测试清理数据库时报 WinError 32 | sqlite3.Connection 的 with 只管理事务，不自动 close；读取使用 contextlib.closing，事务 finally 关闭 | 上下文管理器的职责需要核实 |
| 审批与 Agent 汇总竞态 | 子 Agent 提案后立刻显示可批准；主 Agent 尚未结束，用户批准会令最终状态转换冲突 | 增加 proposal_ready；等主 Agent 结束才发布 awaiting_approval；回归测试复现后通过 | 用户审批必须绑定稳定方案和状态 |
| 候选依赖可变外部代码 | 候选最初导入共享 optimizer.rag_adapter，修改共享文件会改变已保留候选 | 把适配器和配置验证函数冻结进 candidate_retrieval 包；评测实际候选文件；前后校验源文件和产物 | 保存配置不等于冻结实现 |
| 索引未进入完整性指纹 | 只保护代码，vector_index.pt 被排除；更换向量可能不改变候选指纹 | 源指纹用于构建前后检查；索引首次生成后记录完整产物指纹，后续评测、保留复制都复核 | 数据、代码和派生产物均需绑定 |
| 报告路径联接可越界 | 只检查任务根目录，之后拼接的报告/索引路径可能跟随预先存在的 junction 或链接 | 每个报告目录限定在项目内并要求新建；图检查也使用新建目录；真实 Windows junction 写入回归通过 | 只检查根路径不足以约束后续写入 |
| 跨片段证据被误判缺失 | 完整事实被切成两个片段，两片都召回仍得 0 分 | 保存原始证据范围和片段覆盖区间，累计区间并集，再判断完整覆盖；对应测试通过 | 评测标签不能只绑定旧 chunk ID |
| 平均分掩盖原题退化 | 一题从 1 降 0，另一题从 0 升 1，平均召回相同 | 原回归逐题比较 Recall、Precision、MRR、完整覆盖，保存退化 ID；不能以平均不变放行 | 主指标和失败案例都要看 |
| 重启丢失排队任务 | created/approved 等待线程池的任务重启后留在假活跃状态 | 启动将丢失队列及在途状态标记 interrupted；保留审批历史，不自动重放 | 持久化任务状态不等于持久化执行队列 |
| 工具业务参数命名 config | 真实工具调用报 propose_retrieval_plan 缺少 config 参数；与框架运行配置参数发生冲突 | 改名 retrieval_config；检查模型工具 schema，并通过真实框架调度验证 | 框架保留参数不应用作普通业务参数 |
| 嵌入式客户端没有自动加载 Gateway 插件 | 离线测试主子任务已跑通，却没有预算审计事件 | 测试显式按 Gateway 接口加载扩展；生产启动前检查 BudgetContributor 已加载，否则拒绝模型调用 | 配置中声明、插件加载、运行执行是三个证据层级 |
| 单 Agent 对照触发图递归上限 | 60 个图步骤在 4 次模型调用后耗尽，已经提交提案但尚未完整结束 | 保留失败日志，把对照图上限统一为主方案的 80 后成功；费用包含失败尝试 | 图 super-step 不是模型调用次数 |
| 测试夹具替换客户端类不当 | 用函数替换 DeerFlowClient 后，类内静态方法查找报 AttributeError | 改用子类覆盖配置路径；这是测试夹具问题，不归咎于真实客户端 | 测试替身也可能制造假故障 |
| 浏览器会话暂时不可用 | 标签操作返回 browser.user unavailable | 阅读恢复说明，重建 REPL 绑定后重新连接原标签，未改用未授权浏览器控制方式 | 自动化连接故障不等于网页代码故障 |
| 测试依赖弃用提示 | Starlette TestClient 提示未来推荐 httpx2 | 保留上游锁定依赖，当前测试与服务可运行；列为兼容性提醒，没有为了消除提示随意升级 | Warning 与失败要分开判断 |
| 自动审批阶段性阻塞 | 首次真实调用因具体数据发送授权不足被拦截；随后审批服务曾返回额度耗尽 | 用户明确批准模拟政策/问题/检索结果发送至 DeepSeek；正常审批恢复后继续，没有绕过审批 | 预算授权与具体数据发送授权分别记录 |

## 两个真实的负面实验

1. 离线候选“混合检索＋章节切分”：开发集 Recall 达到 100%，留出集却从 95.83% 降到 83.33%。不保留。它说明开发集高分可能掩盖泛化退化，也说明同时改多个因素难以归因。
2. 真实主子 Agent 提出的最小方案“只把 vector 改为 hybrid”：开发集 Recall 96.88%→94.79%，Precision 71.88%→69.79%；留出 Recall 95.83%→83.33%。原题 E02 必要证据覆盖从 100% 降到 50%。用户审阅后明确决定不保留，记录和候选文件继续保存。

本轮没有证明混合检索优于向量检索。第一版的成果是能够提出假设、执行受控实验、发现退化并拒绝不合格改动，而不是预写一个提升数字。

## 推荐学习顺序

先看工具参数冲突和 SQLite 连接释放，再看审批竞态与任务恢复，随后学习证据区间评分、冻结候选、索引完整性，最后分析两个负面实验。每次先复现一个测试，再阅读对应函数，最后解释如果没有这条保护会发生什么。
